Two levels of detail: the whole call, then one turn

How a complete call works, start to finish — then every cache check inside it

This page has two parts. Part 1 is the complete call lifecycle — campaign selection, the live consent/DND/calling-hours gate, dialing, answering-machine detection, the opening disclosure, every exit a call can take (promise-to-pay, escalation, wrong number, callback), and what happens after the call ends. Part 2 is the existing turn-level deep dive — one borrower utterance traced through every cache check, timeout, and service call inside the "TURN LOOP" box that Part 1 treats as a single step.

Part 1 — the complete call lifecycle

Every phase a call passes through, from picking an account to dial through the async post-call analytics/billing/QA loop. The "TURN LOOP" box in Phase 3 is intentionally collapsed here — it repeats once per borrower utterance and is unpacked in full in Part 2, below.

Phase-by-phase walkthrough

Phase 1 — Campaign & dial. scheduler pulls the next overdue account from the loan servicing backend and checks the live consent/DND/calling-hours gate immediately before dialing — not a once-a-day batch filter, since an opt-out registered mid-campaign must take effect within the same second (see docs/security.md). A failed gate check ends the attempt right here — no carrier is ever contacted. A passed check goes to the Carrier Routing Layer, which picks a trunk and an appropriately reputation-managed caller-ID number from a rotated pool (see docs/scaling.md on why number-reputation management is a first-class scaling concern, not an afterthought).

Phase 2 — Connection. The PSTN dial either goes unanswered (voicemail, no-answer, or AMD detects an answering machine) — logged and requeued for a later retry, at zero AI-compute cost since nothing downstream of the carrier is ever touched — or connects, at which point the media server establishes the RTP stream and session-manager creates a fresh session record. call-orchestrator immediately fires the opening turn: compliance's fixed, legally-reviewed disclosure script, streamed out via tts-service before any borrower speech has happened.

Phase 3 — Conversation. Every subsequent borrower utterance runs through the same loop: VAD detects end-of-speech, denoiser cleans the audio, stt-service transcribes it, llm-gateway classifies intent (cache permitting), compliance decides the next state and response (cache permitting), and tts-service streams the reply back — with continuous barge-in monitoring throughout. This loop is what Part 2 of this page unpacks completely; here it's one box because it can repeat anywhere from one turn (an immediate wrong-number or escalation) to a dozen (a long negotiation).

Phase 4 — Resolution. The turn loop exits through exactly one of four doors, decided by compliance's FSM, never by the LLM free-forming an ending: promise-to-pay (compliance's tool-calling module invokes schedulePayment() and updateCRM() before the closing script plays), escalation (full transcript and context handed to a human agent — triggered by an explicit request, a dispute, or detected distress, and this path is reachable from any state in the FSM, not just from within the turn loop's normal flow), wrong number (polite close, number flagged for list removal), or callback requested (a time is scheduled and the account is requeued for a future dial — back into Phase 1 on a later day).

Phase 5 — Post-call. Every resolution path funnels into the same ending: session-manager writes the final state (call_ended=true, outcome recorded), and call-orchestrator emits a call_ended event to Kafka's call.events topic — asynchronously, so none of this can add latency to a call that has, by this point, already ended for the borrower. analytics and billing consume that event independently to update rollup metrics (containment rate, escalation rate, WER) and per-call cost. Escalated calls specifically feed the escalated-call review loop (docs/monitoring.md) — was the escalation actually necessary, or is there a gap in the FSM/model that a future update should close?

12 services — what each one is, and how it scales

One service per pipeline concern (see services/). Scaling tier follows docs/scaling.md: GPU-tier services scale with concurrently-speaking calls (not raw connected calls, since VAD gates silence out before it reaches them); CPU-tier services scale with total concurrent calls; the coordinator scales 1:1 with concurrent calls since it holds no state itself. Row 12 (rag-service) was added after auditing this design against a standard enterprise-conversational-AI checklist and finding a real gap — see docs/architecture.md, "Components added to close an identified gap." Three more candidates from that same audit (tool-gateway, sentiment-detector, model-router) plus a fourth (inference-router) were tried as standalone services in an earlier draft, then folded into llm-gateway/compliance/infrastructure after none of them cleared this design's own criteria for a separate service — see docs/architecture.md, "Consolidated into an existing service, not left as a separate one." (A sixth candidate, voice-biometric fraud detection, was considered and cut entirely — see docs/future-improvements.md.)

Every service, in detail

What each service actually does, why it's split out as its own service rather than folded into another, and what backend it runs today vs. in production. Matches the comment-only specs in services/*/main.py — this is that content, expanded and cross-referenced.

1call-orchestratorcoordinator

Owns one call's pipeline turn-by-turn: takes audio in, calls vad-service → denoiser → stt-service, hands the transcript to llm-gateway for intent, passes (state, intent) to compliance for a decision, and streams tts-service's audio back out — reading and writing all state through session-manager instead of holding any itself.

Why its own service
It's the one piece of logic that must change if the pipeline sequence changes — isolating it means every other service can be swapped or rescaled without touching call-flow orchestration.
State
None. Fully stateless — any replica can pick up any call's next turn, which is what lets it run ~1 lightweight replica per concurrent call.
Dev backend
libs/voice_agent_core/orchestrator/pipeline.py — same sequence, in-process instead of over HTTP.
Depends on
vad-service, denoiser, stt-service, llm-gateway, compliance, tts-service, session-manager, analytics, billing.
2vad-serviceCPU tier

Classifies every audio frame as speech or silence, and tracks the "hangover" window that decides when the borrower has actually finished talking (not just paused) — the single parameter that trades interruption risk against sluggish turn-taking.

Why its own service
Runs on cheap CPU, on the media-server tier — keeping it separate from GPU-tier services means it scales (and is billed) independently of them.
State
Stateful per call: the hangover timer needs to persist frame-to-frame for one call. Sticky-routed to the call's media server in production.
Dev backend
EnergyVAD + HangoverVAD — energy/zero-crossing-rate, no model download.
Production backend
Silero-VAD (ONNX), still CPU-only — a swap behind the same interface.
3denoiserCPU tier

Strips background noise from the borrower's audio before it reaches stt-service — one of the highest-leverage, lowest-cost quality levers available, since ASR errors compound into wrong intents and wrong bot responses.

Why its own service
Lets the denoise model be swapped or A/B tested independently of VAD and STT, even though it sits directly between them in the pipeline.
State
Stateful per call: the noise-floor estimate adapts over the session's duration.
Dev backend
SpectralGateDenoiser — FFT spectral gating, numpy/scipy only.
Production backend
DeepFilterNet (or RNNoise for the lowest-CPU-cost tier) — real-time neural denoising.
4stt-serviceGPU tier

Transcribes the borrower's speech into text. The largest single GPU-compute line item in the whole system (~$0.42M–$1.4M/day depending on scenario, per docs/cost-analysis.md) because it runs continuously for the full duration of every speaking segment, not just briefly per turn like the LLM or TTS.

Why its own service
Needs its own autoscaling group — its throughput profile (continuous, per-speech-duration) is fundamentally different from llm-gateway's or tts-service's (bursty, per-turn).
State
Stateless per request — transcribes one already-VAD-segmented utterance at a time.
Dev backend
MockASR — no acoustic model; reads attached ground-truth text and can inject word-error-rate to simulate realistic imperfection.
Production backend
Self-hosted streaming Conformer / distil-Whisper via CTranslate2 or NVIDIA Riva, continuous-batched.
5llm-gatewayGPU tier

Classifies a borrower utterance into the fixed intent set the compliance FSM understands (promise-to-pay, dispute, hardship, wrong-number, callback-request, escalate, abusive/distress, refuse, affirm, unknown) — and nothing more. It does not decide what the bot says or does next. Also owns sentiment classification (tone: calm/frustrated/distressed/angry) and per-turn model-tier routing (small vs. large model), both folded in from an earlier draft's separate services.

Why its own service, separate from compliance
So a bad model update can never accidentally change what the bot is legally required to say — NLU and call-flow/compliance logic are architecturally impossible to conflate if they're different services.
Why sentiment + model-tier routing are folded in here, not separate services
Both consume the same utterance on the same GPU pool on the same request path as intent classification, and produce sibling outputs compliance reads together — an earlier draft split them out as sentiment-detector and model-router, but neither had a genuinely independent scaling curve or failure domain, so the extra network hop bought no real isolation. See services/llm-gateway/main.py's "FOLDED IN" sections and docs/architecture.md.
State
Stateless — classifies one utterance per request, no memory between calls.
Dev backend
KeywordIntentClassifier — regex/keyword matching, ordered so escalation/distress intents are checked before conversational ones.
Production backend
Fine-tuned 1–3B LLM, served via vLLM/TensorRT-LLM with continuous batching — not a frontier API (see docs/cost-analysis.md for why).
6tts-serviceGPU tier

Synthesizes the bot's spoken response and streams it back — chunk by chunk, so the borrower hears the first word before the whole sentence has finished synthesizing.

Why its own service
Its streaming/cancellation contract (start speaking fast, stop instantly on barge-in) is a distinct concern from everything upstream, and needs to be owned and tested independently.
State
Stateless per request — synthesizes one response utterance as a stream of chunks.
Dev backend
MockStreamingTTS — placeholder audio, but genuine streaming and mid-stream-cancellation semantics for barge-in.
Production backend
Streaming neural TTS (Kokoro-82M-class or Piper), served on GPU.
7compliancestateless

The compliance backbone: owns the finite state machine for the call — mandatory disclosures, negotiation flow, and every escalation trigger (dispute, explicit human request, abuse/distress). Converts "the model should say the required disclosure" into "the model structurally cannot skip it." Also owns tool calling — the single named-function boundary to external systems of record (loan servicing backend, CRM) — folded in from an earlier draft's separate service.

Why this is the most important service in the system
llm-gateway only classifies intent; it never decides the bot's next words or whether to escalate. That decision is a fixed transition table here — a bad NLU day can misclassify an intent, but it can never skip a disclosure or fail to escalate a dispute.
Why tool calling is folded in here, not a separate service
An earlier draft split this out as tool-gateway, reasoning "compliance decides WHAT, tool-gateway decides HOW" — a real distinction, but one that only compliance ever called into, so it never needed its own network hop to stay separable. The WHAT/HOW distinction is preserved as an internal module boundary (a reviewed tool registry and allow-list) instead. See services/compliance/main.py's "FOLDED IN" section.
State
Intentionally none — /transition is a pure function of (current_state, intent). The actual current state is owned by session-manager and round-tripped by the caller on every request, which is exactly what makes this cacheable by (state, intent).
Dev backend
CallFSM + response templates in libs/voice_agent_core/dialogue/.
Example tools
getOutstandingBalance(), schedulePayment(), updateCRM(), requestHumanTransfer().
8session-managerstateful store

The externalized call-state store: current FSM state, account slots, transcript log, escalation flag — for every in-progress call. This is what lets every other service in the system stay stateless.

Why its own service
Centralizing state here is the single design decision that lets call-orchestrator, compliance, and llm-gateway all crash and be replaced mid-call without losing the call.
State
All of it — this is the one genuinely stateful service in the system.
Dev backend
In-memory dict with the same read/write contract the production store would have.
Production backend
Aerospike, keyed by call-id, with per-key TTL and replication ≥2 per partition — chosen over Redis Cluster for its 17-48% lower p99 latency at comparable throughput (both clear the required ~370K ops/sec). Redis Cluster remains a documented alternative if ecosystem maturity is weighted higher.
9schedulerCPU tier

The predictive dialer and the live consent/DND/calling-hours compliance gate — checked immediately before every single dial, not as a once-a-day batch filter, since an opt-out must take effect within the same second it's registered.

Why its own service
Its job (deciding whether a dial is legally permitted right now) is entirely upstream of the call itself — it never touches an active conversation.
State
Reads consent/DND/opt-out state; doesn't own it (that lives in session-manager / the loan servicing backend).
Out of scope here
Real AMD (answering-machine detection) and real dial pacing against live carrier capacity both require a live telephony stack this prototype doesn't have.
10analyticsCPU tier

Logs every call's outcome — final state, escalation, intents seen, turn latency — and computes the rollup metrics that feed the quality-evaluation loop: containment rate, escalation-trigger recall, task success rate, promise-to-pay rate (see docs/monitoring.md).

Why its own service
Pure observability — must be structurally incapable of adding latency to a live call, which is easiest to guarantee by making it a separate, async-only consumer.
State
Owns the event log; doesn't participate in live call state.
Production backend
Kafka topic → analytics warehouse, not a synchronous call from call-orchestrator.
11billingCPU tier

Per-call cost metering, using the same unit-cost assumptions as benchmarks/cost_calculator.py — so a per-call estimate is always consistent with the fleet-level cost model, and specific calls/branches/model-versions can be traced back to the cost they actually drove.

Why its own service
Same reasoning as analytics — cost metering must never sit on the critical path of a live conversation.
State
Owns usage/cost records; doesn't participate in live call state.
Production backend
Kafka-consumed real metering events (GPU-seconds billed, telephony CDRs, agent timesheets), not a synchronous per-call call.
12rag-serviceGPU tiergap-closing

Retrieves the relevant policy/FAQ passage for a borrower question that's real but outside the fixed intent set ("what happens if I miss two payments," "do you report to credit bureaus") — and hands it to compliance as grounded context, never as a bypass of it.

Gap it closes
Without it, an off-script question either matches no intent (re-prompt loop) or escalates unnecessarily — both hurt containment rate for a question that has a real, retrievable answer.
Why its own service
Retrieval is a distinct concern from compliance's job of deciding what's safe/legal to say — compliance still filters every retrieved passage before it reaches the borrower.
State
Stateless per query; the knowledge base itself is a separately-owned, legally-reviewed store.
Low-confidence path
No confident match → treated identically to an unknown intent (re-prompt or escalate), never a low-confidence guess reaching the borrower.
consolidatedtool-gateway, sentiment-detector, model-router, inference-router — folded, not dropped

An earlier draft of this design added these four as standalone services (bringing the total to 16). Auditing that draft against this doc's own criteria for splitting out a service — a genuinely different scaling curve, a compliance/security boundary, or a distinct external vendor integration — found that none of the four cleared it: each shared its scaling curve, deploy lifecycle, and failure domain with a direct neighbor. Rather than ship four self-acknowledged "soft" justifications, each was folded into that neighbor as an explicitly-labeled internal module: tool-gateway → compliance (card 7 above), sentiment-detector and model-router → llm-gateway (card 5 above), and inference-router → shared GPU-serving infrastructure (Triton / vLLM / TensorRT-LLM's own batching layer), not a service at all. See docs/architecture.md's "Consolidated into an existing service, not left as a separate one" and docs/future-improvements.md for the full reasoning.

Sync vs. async — every inter-service call in this diagram, and why

Default assumption: if a call's result changes what the bot says or does this turn, it's synchronous and sits on the latency budget (docs/latency-budget.md). If it doesn't — logging, billing, notifying a queue — it's asynchronous and must never be able to add delay to the audio the borrower hears.

Four cache checks are shown explicitly: session-state (local-to-orchestrator vs. session-manager fetch), intent classification (skips the LLM GPU call entirely for common utterances), the compliance FSM transition (a pure function of state+intent, cacheable by that key), and the TTS phrase cache (skips synthesis for fixed/templated response text). See docs/architecture.md for why each of these is safe to cache, and docs/latency-budget.md for the per-stage timing budget this flow is designed against. Service inventory and scaling tiers match services/ and docs/scaling.md; sync/async choices follow one rule throughout: if it changes what happens this turn, it blocks and counts against the latency budget — if it doesn't, it's fire-and-forget and must never be able to slow down audio already streaming to the borrower.
